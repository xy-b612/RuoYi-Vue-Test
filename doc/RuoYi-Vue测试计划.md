## 1. 测试目标

本次测试围绕若依管理系统 v3.9.2 的核心业务模块展开，目标如下：

| 维度 | 目标 |
|------|------|
| **功能正确性** | 验证所有核心模块功能是否与需求文档一致 |
| **权限安全性** | 验证角色-菜单-按钮三级权限控制是否生效 |
| **数据完整性** | 验证新增/修改/删除操作后数据库状态是否正确 |
| **异常容错性** | 验证非法输入、边界条件、并发操作下的系统表现 |
| **易用性** | 验证界面交互、提示信息、操作流程是否符合用户预期 |

> 📌 **简历定位说明**：本测试为手工功能测试实践，覆盖后台管理系统的典型测试场景，产出物包括测试计划、测试用例、缺陷报告、测试总结，完整呈现测试工程师的日常工作流程。

## 3. 测试策略

### 3.1 测试类型与执行方式

| 测试类型 | 执行方式 | 占比 | 说明 |
|----------|----------|------|------|
| 功能测试 | 手工黑盒 | 75% | 覆盖核心模块的正向/逆向/边界/异常 |
| 接口测试 | Swagger + Postman 手工调试 | 10% | 验证关键接口的输入输出 |
| UI测试 | 手工走查 | 8% | 页面布局、提示信息、分页交互 |
| 兼容性测试 | 手工，Chrome+Edge | 5% | 两大主流浏览器核心流程回归 |
| 安全性测试 | 手工，结合功能测试 | 2% | 权限绕过、XSS、SQL注入探索性测试 |

### 3.2 测试方法

#### 功能测试方法

| 方法 | 适用场景 | 说明 |
|------|----------|------|
| 场景法 | 所有模块 | 模拟真实业务操作流程，如"新建用户→分配角色→登录验证权限" |
| 等价类划分 | 输入型功能 | 有效/无效等价类，如用户名长度、手机号格式 |
| 边界值分析 | 数值/长度输入 | 最小值、最大值、±1 |
| 错误推测法 | 逆向/异常 | 基于经验推断可能出错的地方 |
| 因果图 | 多条件组合 | 如多条件筛选查询 |
| 正交实验 | 配置组合 | 如参数配置组合生效验证 |

#### 接口测试方法

- **工具**：浏览器 Swagger UI（`http://localhost:8080/swagger-ui.html`）+ Postman
- **覆盖**：至少覆盖各模块的 GET 列表查询、POST 新增、PUT 修改、DELETE 删除
- **验证点**：HTTP 状态码、响应 JSON 结构（`code`、`msg`、`data`）、数据库实际落值

### 3.3 回归测试策略

后续每一轮缺陷修复后，回归范围如下：
- **全量回归**：P0 模块登录→用户→角色全链路（每轮必跑）
- **局部回归**：仅回归修复模块及其关联模块
- **探索性测试**：每次回归预留 20 分钟自由探索异常输入

## 7. 缺陷管理规范

### 7.1 缺陷等级定义

| 等级 | 名称 | 定义 | 响应要求 |
|------|------|------|----------|
| **A-致命** | 系统崩溃/数据丢失 | 系统宕机、数据被错误删除、安全漏洞导致越权 | 必须修复才能上线 |
| **B-严重** | 核心功能不可用 | P0 模块主流程无法完成 | 必须修复 |
| **C-一般** | 功能异常但有替代 | 边界处理不当、提示信息不准确 | 建议修复 |
| **D-轻微** | 体验/界面问题 | 排版错乱、文案错别字、非关键提示缺失 | 可延后修复 |
| **E-建议** | 优化建议 | 交互体验改进、性能优化建议 | 非缺陷 |

### 7.2 缺陷状态流转

```
新建(New) → 打开(Open) → 已修复(Fixed) → 关闭(Closed)
                ↓                ↓
             拒绝(Rejected)   重新打开(Reopen) → 打开(Open)
                ↓
             延后(Postponed)
```

### 7.3 缺陷报告模板

```
【缺陷ID】BUG-001
【缺陷标题】【模块名】简短描述问题现象
【严重等级】A/B/C/D/E
【发现版本】v3.9.2
【测试环境】Win11 + Chrome 最新版
【前置条件】使用 admin 账号登录
【重现步骤】
  1. 进入"系统管理 > 用户管理"
  2. 点击"新增"按钮
  3. 不填写用户名，直接点击"确定"
【实际结果】系统提示"保存成功"（或页面报500错误）
【预期结果】应提示"用户名不能为空"
【复现频率】必现
【附件】截图/录屏
【备注】—
```

## 8. 风险管理

| 序号 | 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|------|----------|
| R1 | 新手对业务规则不熟悉，遗漏测试点 | 高 | 中 | 严格对照需求文档BR规则逐条覆盖 |
| R2 | 测试数据污染导致后续用例不可执行 | 中 | 高 | 每次测试前记录初始状态，测试后还原 |
| R3 | Redis 缓存未及时刷新导致结果显示不一致 | 中 | 中 | 修改配置类操作后手动刷新缓存再验证 |
| R4 | 开发环境资源不足导致服务卡顿 | 低 | 中 | MySQL + Redis + 前后端同时运行内存占用较大，注意监控 |
| R5 | 前端热部署失败导致页面不是最新 | 中 | 低 | 测试前强制刷新（Ctrl+F5），必要时重启前端 |
| R6 | 误用 admin 账号测权限控制导致漏测 | 中 | 高 | 权限相关用例统一使用 ry（普通角色）账号 |
